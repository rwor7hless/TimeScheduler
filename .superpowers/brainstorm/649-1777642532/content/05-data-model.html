Как хранить группы — три подхода

До сих пор обсуждали UX. Теперь нужно решить, как это всё держится в БД. Я кратко покажу три варианта и на каком остановлюсь.

A

Отдельная таблица BoardGroup

Модель: BoardGroup(id, user_id, name, sort_order, created_at, updated_at)
Board: + group_id Int? FK BoardGroup ON DELETE SET NULL + sort_order Int
Запросы: для сайдбара 2 запроса (group.findMany + board.findMany), мерджим в дереве на фронте.
Миграция: новая таблица + 2 колонки на boards, дефолт 0 для sort_order, NULL для group_id у существующих 3 досок.
Это рекомендую. Чистая нормальная форма, drag-drop = простой UPDATE, ON DELETE SET NULL аккуратно покрывает удаление группы при выборе «отнести наверх».

B

Self-reference на Board (parent_id)

Модель: Board.parent_id Int? FK Board. Если у Board есть дети — это группа. Если нет — лист.
Минусы: «доска-группа» при этом имеет привязки к Task — что делать с задачами внутри Board, у которой стали дочерние Board? Пришлось бы запрещать. Получается, что у нас уже не Board — а гибрид. Семантика грязная, валидация сложнее.
Не рекомендую.

C

Группы в JSON-поле на User

Модель: User.sidebar_layout Json = [{name, board_ids:[…]}, …]
Минусы: атомарный drag-drop ломается (race на одном поле), нет FK на Board (если board удалён — призрак в JSON), невозможно расширить позже (счётчики, цвета группы и пр.). Самый «лёгкий» по миграции, но платим качеством каждый раз.
Не рекомендую.

Если согласен с A — пиши «ок» в терминал, я перейду к презентации полного дизайна.
